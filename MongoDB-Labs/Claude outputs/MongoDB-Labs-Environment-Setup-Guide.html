MongoDB-Labs — Environment & Atlas Setup Guide

This guide gets you from a fresh machine to a running MongoDB lab notebook, on Windows, macOS, or Linux, and shows you how to connect to MongoDB Atlas. It applies to every lesson (each has a notebook). The capstone, is a design-and-build spec that you build in your own project, so it uses the same setup. Unlike many courses, the labs need no data files: every notebook creates its own data. Do the setup once: one virtual environment and one .env file can serve every lab. Pick one of the three setup paths below; you don’t need all three.

Before you start, you need:

  • Python 3.10 or newer. If you’re not sure whether you have it, see Installing Python.
  • A free MongoDB Atlas account and a free M0 cluster (no payment card needed). Section 10 walks you through creating it and copying your connection string, which starts with mongodb+srv://.
  • Only for the Atlas Search lesson: the fastembed package, which downloads a small embedding model (BAAI/bge-small-en-v1.5) the first time you run the lab, so it needs internet and a few extra minutes.
  • Disk space and time. The install is small: the MongoDB driver and a few helper packages. Setup takes about ten minutes the first time and almost nothing afterwards.
  • Google Colab needs none of the local install — skip straight to Option 2 if you’d rather not install anything locally.

2. Installing Python

Skip this section if python3 --version (macOS/Linux) or python --version (Windows) already prints 3.10 or higher.

Windows

  1. Download the installer from python.org/downloads (the “Windows installer (64-bit)” link).
  2. Run it, and check the box “Add python.exe to PATH” at the bottom of the first screen. This is the step almost everyone misses, and without it none of the commands below will work.
  3. Click Install Now.
  4. Open a new PowerShell or Command Prompt window and confirm: python --version.
  5. Alternative: install from the Microsoft Store (search “Python 3.12”) — it handles PATH automatically.

macOS

The system Python on macOS is old and shouldn’t be used for these labs. Two good options:

  • Homebrew (recommended if you don’t already manage Python another way): install Homebrew from brew.sh, then run brew install python@3.12.
  • Official installer: download the macOS installer from python.org/downloads and run it.

Confirm with: python3 --version.

Linux

Most distributions ship a recent-enough Python. Confirm with python3 --version; if it’s below 3.10, install a newer one with your package manager, e.g.:

sudo apt update && sudo apt install python3 python3-venv python3-pip   # Debian/Ubuntu
sudo dnf install python3 python3-pip                                # Fedora

3. Installing JupyterLab

You only need this for Option 1 (Jupyter Notebook) or Option 3 (VS Code). Google Colab already has Jupyter running in your browser. Each lab’s notebook starts with its own !pip install cell for the packages that lab needs; add jupyterlab and ipykernel to that command if they are not already installed in your virtual environment.

To install it manually (macOS/Linux shown; on Windows use the create/activate commands from the table in Option 1, step 2):

python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install jupyterlab ipykernel

Verify with jupyter --version — it should print a version table including jupyterlab. If you get “command not found” or “jupyter is not recognized”, your virtual environment likely isn’t activated; see the Troubleshooting table.

6. Option 1: Jupyter Notebook (Local)

1. Open a terminal and move into the course folder. You create the virtual environment once, here, and it works for every lab. The commands are the same on Windows, macOS and Linux:

cd MongoDB-Labs   # the folder that holds all the Section folders

2. Create and activate a virtual environment. This keeps the course packages isolated. The create command is the same everywhere; the activate command differs by platform and shell:

python3 -m venv .venv    # macOS/Linux
python -m venv .venv     # Windows
Platform / shellActivate command
macOS / Linux (bash, zsh)source .venv/bin/activate
Windows — Command Prompt.venv\Scripts\activate.bat
Windows — PowerShell.venv\Scripts\Activate.ps1
Windows — Git Bashsource .venv/Scripts/activate

Your terminal prompt should now show (.venv) at the start of the line. (PowerShell note: if you get a “running scripts is disabled” error, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once, then retry.)

3. Install the packages. Each notebook’s first code cell is a !pip install line with exactly the packages that lab needs, and the lab’s own “Environment / Dependencies Setup” section repeats it. Installing the shared set once covers every lesson, and the Atlas Search lesson adds one package:

pip install --upgrade pip
pip install jupyterlab ipykernel
pip install -q "pymongo[srv,tls]==4.10.1" python-dotenv==1.0.1 certifi
pip install fastembed          # Atlas Search lesson only

4. Set up your .env file. Create it in the MongoDB-Labs folder (see Section 9 for details and the Atlas steps in Section 10 to get the value). Replace the placeholder with your own connection string:

# macOS / Linux / Git Bash
printf 'MONGODB_URI=mongodb+srv://<user>:<password>@<cluster-host>/\n' > .env
# Windows PowerShell
Set-Content .env 'MONGODB_URI=mongodb+srv://<user>:<password>@<cluster-host>/'
# Windows Command Prompt
echo MONGODB_URI=mongodb+srv://<user>:<password>@<cluster-host>/> .env

5. Check that the connection works. From the course folder, with the environment active:

python -c "import os,certifi,pymongo; from dotenv import load_dotenv; load_dotenv(); print(pymongo.MongoClient(os.environ['MONGODB_URI'], tlsCAFile=certifi.where()).admin.command('ping'))"

It should print {'ok': 1.0}. If it does not, go to Troubleshooting.

6. Launch Jupyter and open the notebook. Move into the lab folder you are working on, then start Jupyter there:

cd "Section 1 - Foundations/Lab 1 - Student Records Lookup"
jupyter lab lab-1-student-records-lookup.ipynb    # replace with this lab's .ipynb filename

Run each cell top to bottom with Shift+Enter. Don’t skip ahead — later cells depend on variables created earlier. The labs find your .env file by themselves, because load_dotenv() looks in the folder you run from and then in each parent folder above it.

7. When you’re done, run deactivate (optional, but tidy).

7. Option 2: Google Colab

Colab runs in your browser on Google’s servers, so there is nothing to install, but it has no persistent disk by default. That affects your packages and your connection string.

1. Open the notebook. Go to colab.research.google.com → File → Upload notebook, and select the lab’s .ipynb file.

2. Install packages in a cell. Run the notebook’s own first cell, the one that starts with !pip install. Colab keeps some preinstalled packages, so a restart prompt can appear; if it does, restart the runtime and continue from the next cell.

3. Allow Colab to reach Atlas. Colab connects from Google’s servers, whose addresses change, so your own IP address will not work. In Atlas, open Network Access and allow access from anywhere (0.0.0.0/0). Do this only on a practice cluster that holds no real data, and remove the entry when you finish.

4. Provide your connection string the secure way. Do not paste it into a code cell. Use Colab Secrets: click the key icon in the left sidebar → Add new secret → name it MONGODB_URI → paste the value → toggle Notebook access on. Then load it before the lab’s own load_dotenv() cell:

import os
from google.colab import userdata
os.environ["MONGODB_URI"] = userdata.get("MONGODB_URI")

5. Alternative: write a real .env. Run %%writefile .env in a cell with the MONGODB_URI=... line. It is wiped whenever the runtime disconnects, so Secrets is the better default.

6. No data to upload. The labs create their own data inside Atlas, so there are no files to bring into Colab. Run the notebook top to bottom with Shift+Enter. The Colab disk is deleted when the runtime is recycled, so repeat step 2 at the start of each new session (your Secret is already saved).

8. Option 3: VS Code

VS Code is identical across Windows, macOS and Linux; the only differences are the same venv-activation and file-creation commands shown in Option 1.

  1. Install two extensions (Ctrl+Shift+X on Windows/Linux, Cmd+Shift+X on macOS): Python and Jupyter, both published by Microsoft.
  2. Open the course folder. File → Open Folder… and select MongoDB-Labs. Because your .env file sits at the top of this folder, every lab finds it.
  3. Create a virtual environment. In the built-in terminal (Ctrl+`) run the create/activate commands from Option 1, step 2. Or use the Command Palette → “Python: Create Environment” → Venv.
  4. Install the packages as in Option 1, step 3.
  5. Select the interpreter. Command Palette → “Python: Select Interpreter” → choose the .venv you created. This is the step people miss most often; with the wrong interpreter, imports fail even though you installed the package.
  6. Create your .env. Explorer panel → New File → name it exactly .env → type the MONGODB_URI=... line → save. This works the same on every platform.
  7. Open the .ipynb directly in VS Code, click the kernel picker in the top right to confirm it uses your .venv, then run cells with Shift+Enter.

9. Creating and Configuring Your .env File

What it is and why it matters

A .env file is a small plain-text file that holds your secrets outside your code. Every MongoDB notebook calls load_dotenv() at the start, which reads this file and puts its values into os.environ. The code then reads os.environ["MONGODB_URI"] instead of having your connection string typed into a cell. This matters because your connection string contains your database password, and code gets shared and committed to git; secrets shouldn’t be.

One file for the whole course

load_dotenv() looks for a file named .env in the folder you run from and then in each parent folder above it. So a single .env saved in the MongoDB-Labs folder is found by every lab, and you never need to copy it. (Saving it next to a notebook also works.) The file needs just one line:

MONGODB_URI=mongodb+srv://<user>:<password>@<cluster-host>/?retryWrites=true&w=majority

Ways to create the file by hand:

WhereHow
macOS/Linux terminalnano .env (or vim .env), type the line, save and exit
Windows — PowerShellNew-Item .env then notepad .env
Windows — Command Prompttype nul > .env then notepad .env
Windows — Notepad directlyFile → Save As → filename .env, and change “Save as type” to All Files (otherwise Notepad silently saves .env.txt)
VS Code (any platform)Explorer panel → New File → name it .env → type the line → save
Google ColabUse Colab Secrets, or %%writefile .env in a cell (see Option 2)

A few details that trip people up, on any platform:

  • No quotes needed around the value, and no spaces around the =: KEY=value, not KEY = value.
  • The filename is exactly .env — a leading dot and no extension. Check it in your file browser with file extensions turned on.
  • Replace <password> with your real password and remove the angle brackets. If the password contains special characters such as @, : or /, write them in percent-encoded form (@ becomes %40), or generate a simpler password in Atlas.
  • Keep the mongodb+srv:// prefix exactly as Atlas shows it. The +srv form looks up your cluster’s servers by name, and it always uses an encrypted (TLS) connection.
  • Save, then re-run the load_dotenv() cell. Values are loaded once, when that cell runs, so after editing the file re-run the cell (or restart the kernel).

Keeping it safe

  • Never commit .env to git. Add it to your .gitignore and double-check with git status before pushing.
  • Never paste your real connection string into a notebook cell, a chat, or a screenshot.
  • If it leaks, change the database user’s password in Atlas straight away (Database Access → Edit), then update your file.

10. MongoDB Atlas Setup (free M0 cluster)

Every lab runs against a real MongoDB Atlas cluster. The free M0 tier is enough for all of them. Do these steps once.

Create the cluster and a database user

  1. Go to mongodb.com/atlas, sign up or log in.
  2. Create a new deployment and choose the Free (M0) tier. Pick the cloud provider and region nearest to you and give it a name (for example Cluster0).
  3. Wait a minute or two while the cluster is created.
  4. Create a database user (Database Access → Add New Database User). Choose password authentication, enter a username and a password, and keep the default privileges. Write the password down: you need it for the connection string.

Let your computer connect

  1. Open Network Access → Add IP Address → Add Current IP Address, then confirm.
  2. If your IP address changes (a new network, a VPN, a laptop that moves between locations), add the new address here too.

Copy your connection string

  1. Open your cluster → Connect → Drivers → choose Python.
  2. Copy the connection string. It looks like mongodb+srv://<user>:<password>@<cluster-host>/?....
  3. Replace <password> with your database user’s password and paste the whole line into your .env file after MONGODB_URI=.

Test it

Run this in a notebook cell or a Python file. It should print a result with ok equal to 1.0:

import os, certifi, pymongo
from dotenv import load_dotenv
 
load_dotenv()
client = pymongo.MongoClient(os.environ["MONGODB_URI"], tlsCAFile=certifi.where())
print(client.admin.command("ping"))    # {'ok': 1.0}

Warning: the labs drop and recreate their own collections each time you run them (see Data and Collections), and the capstone drops a whole database at the end. Use a practice cluster, not one that holds data you care about.

11. Data and Collections

Unlike a course that reads files from disk, every MongoDB lab creates its own data inside your Atlas cluster, so there is nothing to download and no data/ folder to check. What you need to know is which collections each lab creates and drops, so that you never lose something you care about. The labs fall into three patterns.

Pattern A — Small data written in the notebook

The first nine lessons insert a few dozen documents typed directly into the notebook (for example 25 student records). They are all stored in a database called school_db that is created automatically the first time you insert.

Pattern B — Data the notebook generates

The Query Optimization lesson generates 100,000 enrollment records with a fixed random seed, so you get the same data every time (about 20–30 MB). the Schema Patterns lesson generates its own pattern data. The capstone seeds 30,000 enrollments in a separate database, registrar_db. Generation takes a few seconds to a minute.

Pattern C — Data plus a model download

The Atlas Search lesson turns 22 course descriptions into numbers with fastembed and the model BAAI/bge-small-en-v1.5. The model is downloaded on the first run and then cached, so the first run is slower and needs internet.
